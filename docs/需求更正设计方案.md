# 售前智能体需求更正设计方案

## 1. 背景

本次需求更正来自客户交流会议后的反馈。当前工具已经具备客户交流会议 SOP、A/B/C 交流类型、推荐问题和 AI 生成建议能力，但实际测试发现：选择 A 类、B 类、C 类后，AI 输出内容差异不明显，甚至出现基本一致的情况。

根因不是单一提示词问题，而是当前架构仍以统一 7 步 SOP 为主流程，A/B/C 只是附加的会议打法参考。前端展示、后端上下文和推荐问题都围绕通用 SOP 组织，导致模型容易回到统一流程，无法稳定按当前会议类型输出。

本方案用于明确第一阶段调整范围：先解决分类入口、内容结构、AI 上下文和差异化测试问题；视觉大改和模型设置页放到第二阶段。

## 2. 设计原则

1. 保留专家经验，不重写成泛化内容。
2. 沿用现有 SOP、Skill、会议打法中的具体关注点、必做项、常见错误、风险边界和输出建议。
3. 将专家经验按 A/B/C 三类重新归类、裁剪和提炼为更短的大节点流程。
4. 前端只展示当前类型 SOP。
5. 后端只注入当前类型 SOP。
6. AI 不得回退、引用或混用其他类型 SOP，也不得默认按 A 类处理。
7. 信息不足时列为“需补充信息”，不得编造客户背景、预算、友商评价、产品能力或项目事实。

## 3. 第一阶段范围

第一阶段必须完成：

- 半强制入口弹窗。
- A/B/C 专属客户信息采集字段。
- A/B/C 专属 SOP 数据重组。
- A/B/C 专属推荐问题。
- 前端只渲染当前会议类型的 SOP。
- 后端只基于当前会议类型构建 AI prompt。
- 新增差异化测试，覆盖 A/B/C 三类。

第一阶段暂不做：

- 大节点视觉重做。
- 节点详情白底黑字弹窗。
- checklist 完成状态和步骤解锁。
- 色块视觉体系重做。
- 模型设置页和模型切换 UI。
- Excel 或其他文件导出能力。

## 4. 入口交互

用户进入“客户交流会议”场景后，先出现会议信息采集弹窗。

交互规则：

- 必须选择会议类型：A / B / C。
- 选择类型后展示该类型对应的信息字段。
- 客户信息字段允许“不清楚/待补充”。
- 用户选择会议类型后即可进入工作台。
- 工作台顶部持续显示当前会议类型、客户名称和信息完整度。
- 未选择会议类型时，不允许发送 AI 请求。
- 已选择类型但信息不完整时，允许发送 AI 请求，但 prompt 必须包含缺失字段提醒。
- 用户切换会议类型时，应提示当前 SOP、推荐问题和 AI 上下文将随类型切换。

## 5. 客户信息采集字段

### 5.1 A 类：初步宽泛交流

A 类用于新客户首次交流或客户希望宽泛了解公司和整体能力的场景。

建议字段：

- 客户单位名称：必填或待补充。
- 主营业务：必填或待补充。
- 所属领域：必填或待补充。
- 本次交流发起原因：选填或待补充。
- 参会对象：选填或待补充。
- 已知历史接触情况：选填或待补充。

### 5.2 B 类：意向方向深入交流

B 类用于客户已经对某个方向有兴趣，需要进一步拆解业务场景、角色、数据和系统条件的场景。

建议字段：

- 客户单位名称：必填或待补充。
- 具体科室或业务方向：必填或待补充。
- 客户关注的产品/能力/方向：必填或待补充。
- 决策者或关键影响人：选填或待补充。
- 客户对产品或方向的态度：选填或待补充。
- 已有系统建设情况：选填或待补充。
- 友商、内部系统或预算线索：选填或待补充。
- 数据来源或样例情况：选填或待补充。

### 5.3 C 类：方案汇报推进交流

C 类用于已有方案、Demo、POC 结果或阶段成果，需要向客户汇报并推动下一步动作的场景。

建议字段：

- 客户单位名称：必填或待补充。
- 本次汇报对象：必填或待补充。
- 汇报目标：必填或待补充。
- Demo 或方案准备情况：必填或待补充。
- 已有共识：选填或待补充。
- 待确认问题：选填或待补充。
- 希望客户会后给出的动作：选填或待补充。
- 是否涉及试用、POC、立项或扩大试点：选填或待补充。

## 6. A/B/C 专属 SOP

### 6.1 A 类：初步宽泛交流

目标：建立客户认知、发现兴趣方向、确认后续科室。

建议 5 个大节点：

1. 客户基础调研
2. 交流背景与参会对象判断
3. 公司能力与材料准备
4. 初次交流现场引导
5. 会后兴趣判断与下一次交流

A 类重点：

- 保留客户调研环节。
- 关注客户主营业务、组织背景、历史接触、已有系统、同类软件、差分点准备。
- 现场不要过早进入需求分析、数据字段、接口和 POC 条件。
- 会后重点输出兴趣方向、跟进科室、关键联系人、已有系统线索和下一次交流主题。

### 6.2 B 类：意向方向深入交流

目标：把客户兴趣方向拆成可判断的业务场景，确认数据、角色、系统和 POC 可能性。

建议 6 个大节点：

1. 已知兴趣方向确认
2. 业务场景与真实问题拆解
3. 使用角色与决策链确认
4. 数据、已有系统与友商情况确认
5. POC/方案深化条件判断
6. 会后信息缺口与下一步分流

B 类重点：

- 不再做宽泛客户调研作为主流程。
- 不把客户提出的功能点直接当正式需求。
- 必须追问业务流程、岗位、场景、当前做法、痛点、数据来源、已有系统和成功标准。
- POC 判断必须基于数据明确、客户配合、价值明确、有评价人和范围可控。
- 会后重点输出真实问题、初步业务场景、数据条件、已有系统情况、信息缺口和下一步建议。

### 6.3 C 类：方案汇报推进交流

目标：基于已有方案、Demo 或 POC 结果，推动客户反馈、决策和下一步行动。

建议 6 个大节点：

1. 汇报目标与决策对象确认
2. Demo/方案准备状态检查
3. 价值逻辑、边界与风险梳理
4. 方案汇报现场反馈收集
5. 试用/POC/立项条件判断
6. 会后决策事项与行动清单

C 类重点：

- 跳过 A 类客户基础调研作为主节点。
- 重点检查方案、Demo、视频、截图、离线材料、脱敏、备用材料和试用边界。
- 不能夸大 POC 结果，不能承诺价格、周期、效果、成熟度和固定交付范围。
- 现场重点收集客户认可点、质疑点、补充要求和决策事项。
- 会后重点输出客户反馈、待补充内容、决策链、关键推动人和下一步行动项。

## 7. 节点详情结构

每个大节点内部统一保留以下折叠详情结构：

- 关注点
- 必做项
- 建议项
- 经验提醒
- 常见错误
- 可问 AI
- 输出建议
- 不可承诺/需内部确认

当前第一阶段可继续沿用现有详情展示方式，数据结构先调整到位。第二阶段再将详情改为白底黑字弹窗和折叠块视觉。

## 8. 数据结构调整

### 8.1 场景配置

建议将 `scene_config.json` 从统一 `sopNodes` 改为按会议类型组织：

```json
{
  "sceneId": "customer_communication",
  "sceneName": "客户交流会议",
  "meetingTypes": [
    {
      "id": "A",
      "name": "初步宽泛交流",
      "intakeSchema": [],
      "sopNodes": []
    },
    {
      "id": "B",
      "name": "意向方向深入交流",
      "intakeSchema": [],
      "sopNodes": []
    },
    {
      "id": "C",
      "name": "方案汇报推进交流",
      "intakeSchema": [],
      "sopNodes": []
    }
  ],
  "globalGuardrails": []
}
```

全局 `globalGuardrails` 只保留边界规则，不再承载流程规则。

### 8.2 推荐问题

建议将 `recommended_questions.json` 改为按会议类型和 SOP 节点组织：

```json
{
  "sceneId": "customer_communication",
  "byMeetingType": {
    "A": { "bySopNode": {} },
    "B": { "bySopNode": {} },
    "C": { "bySopNode": {} }
  }
}
```

推荐问题不再跨类型共享。A 类推荐初次交流准备问题，B 类推荐业务场景和数据条件问题，C 类推荐方案汇报和风险回应问题。

## 9. AI 上下文与提示词规则

后端 `buildChatMessages` 必须按当前会议类型构建上下文。

必须注入：

- 当前会议类型。
- 当前类型客户信息。
- 缺失字段清单。
- 当前类型专属 SOP。
- 当前 SOP 节点。
- 当前节点详情。
- 当前类型会议打法。
- 当前类型推荐问题。
- 最近对话。
- 全局边界规则。

不得注入：

- 通用 7 步 SOP。
- 其他会议类型 SOP。
- 其他会议类型推荐问题。
- 其他会议类型打法，除非用户明确要求切换类型，此时也应提示用户切换会议类型，而不是混用。

强制回答规则：

```text
你只能依据当前会议类型的专属 SOP 输出建议。
不得引用、回退或混用其他会议类型 SOP。
不得默认按 A 类宽泛交流处理。
信息不足时列为需补充信息，不得编造。
如果用户问题明显属于其他会议类型，应建议用户切换会议类型，而不是混用流程。
```

## 10. 前端状态调整

建议新增或调整以下状态：

- `meetingType`：当前会议类型，未选择时为空。
- `customerContext`：入口采集的客户信息。
- `missingContextFields`：缺失字段清单。
- `intakeCompleted`：是否已完成类型选择。
- `currentSopNodeId`：当前类型下的 SOP 节点。
- `completedNodeIds`：已完成节点。
- `selectedRecommendedQuestion`：当前类型和节点下的推荐问题。

前端渲染规则：

- 未选择会议类型时，不渲染 SOP 工作台或以弹窗覆盖。
- 选择 A 只渲染 A 类 SOP。
- 选择 B 只渲染 B 类 SOP。
- 选择 C 只渲染 C 类 SOP。
- 推荐问题只来自当前类型和当前节点。
- AI 发送请求必须包含 `meetingType` 和 `customerContext`。

## 11. 测试标准

第一阶段必须补充以下测试：

- 未选择 A/B/C 时，前端不允许发送 AI 请求。
- 选择 A 后，前端只渲染 A 类 SOP。
- 选择 B 后，前端只渲染 B 类 SOP。
- 选择 C 后，前端只渲染 C 类 SOP。
- A/B/C 三类使用同一个用户问题时，后端 prompt 背景必须不同。
- A 类 prompt 包含 A 类客户调研和初次交流内容，不包含 C 类 Demo/方案汇报主流程。
- B 类 prompt 包含业务场景、角色、数据、已有系统和 POC 条件，不包含 A 类宽泛介绍主流程，也不包含 C 类方案汇报主流程。
- C 类 prompt 包含 Demo/方案、价值逻辑、风险边界、客户反馈和决策事项，不包含 A 类客户基础调研主流程。
- 客户信息缺失时，prompt 必须包含缺失字段提醒。
- 推荐问题随会议类型和当前节点变化。

## 12. 第二阶段规划

第二阶段在第一阶段稳定后进行，主要优化视觉与操作体验：

- SOP 节点做成更大的独立大框。
- 点击节点后用白底黑字弹窗展示详情。
- 详情内容改为可折叠块。
- 增加 checklist 打勾能力。
- 对未完成前置步骤的后续节点做提醒，但不建议硬锁死。
- 用色块区分关注点、必做项、常见错误、风险提醒等内容类型。
- 增加模型设置页，支持默认 API 和模型切换。

## 13. 验收结论

第一阶段完成后，应能明确验证：A、B、C 三类会议在 SOP 流程、推荐问题、AI prompt 和模型输出方向上均存在结构化差异。用户选择某一类型后，系统不会再回到通用 SOP，也不会混用其他类型流程。
