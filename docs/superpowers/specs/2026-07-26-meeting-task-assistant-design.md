# 会议任务助手第一版设计

## 目标

将当前“先选择 A/B/C、填写客户信息、选择 SOP 节点后再提问”的售前学习型问答界面，改造成自然语言驱动的会议任务助手。

用户通过一句需求、粘贴会议纪要或上传 Word 文档，即可获得可直接使用的会前准备、会中追问或会后复盘与下一步跟进方案，并可导出为 Word。系统继续调用公司内网兼容 OpenAI Chat Completions 的模型服务，默认模型为 `ziwigpt-kinetic`。

## 范围

第一版支持三类任务：

- 会前准备
- 会中下一问
- 会后复盘与下一步跟进

用户可以点击任务按钮，也可以直接输入自然语言。没有显式选择任务时，系统自动判断；判断不确定时，只提出一个关键澄清问题。

系统继续使用 A/B/C 会议类型、会前/会中/会后 SOP、推荐问题与风险约束，但不再把它们设为使用前置条件。自动判断出的会议类型和阶段在结果中展示，用户可以手动更正后重新生成。

## 非目标

- 不接入会议录音、实时语音转写或说话人识别。
- 不接 CRM、邮件、日历或待办系统。
- 不自动向外部系统写入或发送内容。
- 不新增长期客户档案或会议历史持久化。
- 不在第一版提供 MCP 服务。

## 用户流程

1. 用户打开工作台，在主输入框输入需求、粘贴纪要或上传 Word 文档。
2. 用户可选择任务按钮；未选择时由服务端根据输入判断任务。
3. 服务端确定任务、推断会议阶段和 A/B/C 倾向，并从输入与附件中抽取可用上下文。
4. 若任务不可判断或缺少阻塞性信息，返回单个澄清问题；用户补充后再次提交。
5. 服务端将任务、上下文、现有 SOP/模板/风险规则组装为模型消息，调用内网模型流式返回结果。
6. 前端展示任务结果、系统判断和可更正入口；用户可以继续追问、复制结果或下载 Word。

## 前端设计

主界面以任务输入为中心：

- 一个多行自然语言输入框。
- 三个任务按钮：会前准备、会中下一问、会后复盘与下一步跟进。
- 原有 Word 上传能力保留。
- 结果区显示任务、会议类型和阶段的判断结果，以及模型生成的结构化内容；结果区提供“导出 Word”命令。
- A/B/C 与 SOP 改为可选的“判断依据/手动修正”区域，不再在首次进入时强制弹出 intake 表单。

第一版不移除旧 SOP 页面能力；旧配置继续作为后端规则来源，并保留为手动纠正入口。

## 服务端设计

新增独立的任务处理层：

- `taskRouter.js`：规范化显式任务；未显式选择时使用轻量规则判断任务和阶段。规则无法可靠判断时返回澄清状态，而不是编造判断。
- `taskExecutor.js`：从用户输入、附件和可选的人工纠正中构建任务上下文，并调用 Prompt 构建函数。
- `promptBuilder.js`：保留现有 SOP、客户信息、附件、会话历史和风险规则的拼装能力，增加任务型输出规则；不再要求请求必须先携带 A/B/C。
- `server.js`：新增流式任务接口，保留现有聊天接口以避免破坏旧路径。

模型任务输出先以受限 Markdown 结构返回。服务端将结果解析为标题和黑点列表，再由本地 Word 生成器套入公司会后复盘模板，生成 `.docx` 文件供用户下载。会后复盘使用明确的标题结构；标题下统一使用黑点列表的既有规则继续保留。

## 会议类型推断

第一版采用保守策略：

- 用户显式选择 A/B/C 时，优先使用用户选择。
- 输入中出现首次沟通、初步了解、需求背景等信号时，倾向 A。
- 出现数据条件、系统现状、试点范围、详细需求等信号时，倾向 B。
- 出现方案汇报、Demo、POC、立项、决策等信号时，倾向 C。
- 信号不足时，会议类型标记为“待确认”，不阻断任务执行；仅在需要使用类型专属 SOP 时提出一个简短问题。

## 测试与验收

- 任务按钮应把对应任务传递到任务接口。
- 用户不选择 A/B/C 时，会前准备、会中下一问、纪要整理和邮件生成均可提交。
- 规则可识别典型的 A/B/C 表述，无法识别时不伪造确定结果。
- 上传 Word 后，附件文字可进入任务上下文。
- 会后复盘结果包含客户信息、会议结论、待确认事项、客户侧/我方行动项、下一步建议和推进判断。
- 用户可将会后复盘结果导出为 Word；导出的标题和黑点列表与页面结果一致。
- 现有 SOP、附件、Markdown 黑点列表和模型配置测试持续通过。

## 技术约束

- 保持 Node.js 原生 HTTP 服务和原生前端技术栈，不为第一版引入前端框架。
- 保持默认内网模型地址与 `ziwigpt-kinetic` 配置，可继续用环境变量覆盖。
- 第一版不要求数据库和新增第三方服务。
